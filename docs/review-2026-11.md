# Code review — November 2026

A bug hunt over the whole repository, plus the improvements and features I would build next. Everything in
"Fixed in this pass" is committed on `claude/youthful-gates-aktwsg`; everything under "Open" is not, and each
entry says what the fix looks like so it can be picked up in order.

Test state at the time of writing: 372 unit tests pass on DuckDB and on PostgreSQL 16, 10 Playwright
end-to-end tests pass, `bandit` reports nothing at medium severity or above.

## Fixed in this pass

Measured with throw-away probes against a synthetic history (20,000 settled auctions and 20,000 finished
deals) — roughly what a busy year looks like.

| What was wrong | Effect | After |
|---|---|---|
| A finished deal was re-serialised and re-hashed on **every** state flush for 40 days (`MATCH_FREEZE_MS`) | **197 ms of event-loop time every second** at 20k deals, growing linearly — at ~100k deals the app stops answering | 10 ms. A deal freezes once it settles; the three dispute paths that can still edit it now call `Store.thaw`, which is what makes a late ruling reach the database anyway |
| `matches.expire_stale` walked every deal ever made, twice, on the 50 ms tick | 2.8 ms per tick at 20k deals (≈6% of the loop), linear | 0.5 ms — an index of deals still in flight |
| `recompute_reputation` scanned every deal to score one agent | 18 ms per call, two calls per settled deal | 0.005 ms — an index of deals by party |
| `orchestrator.consider` marked an (agent, auction) pair considered *before* the strategy ran and never released it on failure | A transient error — a provider blow-up, a database hiccup, a trigger lost to a race — **silently retired that auction for that agent for good**: no bid, no notification, no retry | The key is released and the next event plans normally |
| `kb.search` re-tokenised and re-counted the whole knowledge base on every search | 26 ms per search per 0.5 MB of documents, on the loop, for every agent decision that uses the tool | 8 ms; documents are indexed once (they are immutable once added) |
| `compute_kpis` ran per viewer on a 3-second timer | 18 ms × every open `/platform` page | One computation per 2-second window, shared |
| A password reset left the re-authentication lockout in place | After five wrong tries at a sensitive form, a reset did not restore access to it for five minutes | Cleared with the password it belonged to |
| A session cookie naming a deleted account was re-checked on every page load | Minor | Dropped on sight |
| `anthropic>=1.0` resolved to 2.x, which changed its auth header and vendored its own `httpx2` | A build today is not the library the code was tested against | Majors pinned in `requirements.txt` and `pyproject.toml` |
| The shipped compose stack is PostgreSQL, and the app's backup service only supports DuckDB | **The production stack ran with no backups at all** | A `backup` service: nightly `pg_dump -Fc`, each dump proved readable with `pg_restore --list`, retention in days, a failed dump kept as `.bad` with retention skipped so a broken run cannot age out the last good copy |

## Open — ranked by what I would do first

### 1. Nothing is ever archived out of memory (the real scaling ceiling)

Closed auctions, finished deals, users and agents all stay in RAM for the life of the process; `Store.prune`
bounds only the append-only logs. Measured: **~2.7 KB of resident memory per completed deal** (auction +
match), so a million deals is ~2.7 GB before counting the digest maps the persistence layer keeps alongside
them. Fine for year one, fatal by year three.

The database is already there and already holds every record. What is missing is a read path that does not
need the whole history resident: move records closed more than N days ago out of `store`, and serve them from
SQL on demand (the auction page, `/activity`, CSV exports, reports). `engine.browse()` and the new match
indexes are the pattern — they already only touch what is open. This is the one piece of work that changes
the product's ceiling rather than its constant factors.

### 2. One process, by design

The writer lease means exactly one app instance, and the throttles, lockouts, token holds and per-IP budgets
live in its memory. Two consequences worth deciding about deliberately:

* **No zero-downtime deploy.** Restarting drops the lease and every websocket. Add a `SIGTERM` drain (stop
  accepting, finish in-flight decisions, final flush, release lease) and document the window; or accept it and
  schedule restarts.
* **No horizontal scale.** Before a second replica is possible: throttles and lockouts in Redis, auction
  sharding, and a shared view of token holds. I would not build that until the single process is measurably
  the constraint — but the limit belongs in `SECURITY.md` next to the rate-limit note, which already says it.

### 3. The sign-in path scans every account

`AgentService._find` is a linear scan over `store.users`, and it runs *before* the password check:
**3.0 ms per sign-in attempt at 20,000 accounts**, 15 ms at 100,000, on the event loop. The per-IP throttle
bounds one attacker, not a distributed one. `create_user` and `set_phone` scan the same way.

The fix is a `name_lower -> id` / `phone -> id` index on the Store, like `MatchIndex`. I deliberately did
**not** write it in this pass: a stale name index locks a real user out of their own account, and every write
that touches a name or phone (including the alias `privacy.delete_account` assigns) has to go through one
choke point for that not to happen. It is half an hour of work and worth doing carefully, with a test that
renames an account and signs in again.

### 4. Channel commands can raise limits

A WhatsApp message can run `ceiling <amount>` with no upper bound, and `approve <id>` on a pending bid. In a
market where SIM swap is a routine attack, that is the weakest link in an otherwise careful auth story: the
web app demands a password and 2FA, WhatsApp demands possession of a phone number.

I would make channel commands **narrowing only** — `pause`, `reject`, lowering a ceiling — and require the
web session (or a per-user channel PIN) for anything that increases exposure. `approve` should additionally be
capped by an amount the user sets in the web app.

### 5. Smaller things

* **DNS rebinding on admin-configured URLs.** `check_outbound_url` and `kb._check_public_url` resolve the host,
  then let `httpx` resolve it again when connecting. Pin the checked address into the connection for LLM, MCP
  and knowledge-base fetches.
* **`on_auction_created` fans out over every agent** for every new listing. Index agents by watch category.
* **No `Origin` check on the websocket upgrade.** The session cookie is `SameSite=Lax` and `https_only` in
  production, which covers the realistic cases; an explicit check is cheap belt-and-braces.
* **Wallet integrity is verified only at startup** and on an admin click. Run it on a schedule and alert.
* **`ui.common.left()` reads the wall clock** while everything else reads the injected clock — harmless in
  production, wrong under a fake clock.
* **No load test.** The scale tests added in `tests/test_scale*.py` are the beginning of a performance gate;
  a k6 or Locust scenario (50 bidders, one hot auction) would catch regressions the unit suite cannot.
* **No request ids or error sink.** `/metrics` and `/readyz` cover liveness, not "which click failed for which
  user". The UI already mints a reference per unexpected error — put that id in the log line and ship logs
  somewhere searchable.

## Features I would build next

Ordered by value per unit of effort, with the honest cost attached.

**The three that would define the product**

1. **Settlement, not just introduction.** The platform deliberately never touches deal money, and that is the
   single biggest trust gap: "will the goods arrive / will I be paid" is exactly what stops a Nairobi SME
   buying from a stranger. Escrow against M-Pesa (funds held until both sides confirm) converts the existing
   match-and-confirm flow into a guarantee. **Cost: regulatory, not technical** — holding client funds in
   Kenya means a CBK-licensed partner or a payment service provider licence. Worth scoping now even if it
   ships through a partner, because every other trust feature is a substitute for it.
2. **Demand aggregation.** Pool several SMEs' RFQs for the same item into one volume RFQ, award it, and split
   delivery. This is where agents genuinely beat a human buyer — no individual shop can assemble a
   twenty-tonne order by Tuesday — and the reverse-auction engine, the guardrails and the match flow already
   exist. The hard parts are splitting an award across buyers and apportioning delivery. Highest product
   upside of anything on this list that does not need a licence.
3. **Logistics attached to the match.** "Not delivered" is the first dispute category for a reason. A delivery
   quote per match (boda, pickup, truck aggregators) turns the riskiest step into a line item, and it is a
   second revenue stream that needs no licence.

**Cheap wins, in rough order of effort**

4. **Agent presets per category.** "Maize wholesaler", "electronics retailer", "hardware supplier" — a
   one-click bundle of constraints, watch spec and strategy. The configuration surface is the main thing
   between a new sign-up and a working agent.
5. **Proactive supplier matching.** Suppliers register what they can supply; the engine pushes matching RFQs
   to them instead of waiting for them to watch a category. The watch-alert machinery already does the work;
   this is a different default.
6. **A public price index.** `market_history` already holds clearing prices per category. Publish a weekly
   index — free marketing, a reason for the press to link to you, and eventually a data product. Near-zero
   build cost.
7. **The agent's own timeline.** Every decision, guardrail verdict and token cost for one auction, in order.
   The audit log already records all of it; this is a page, not a feature. It is also the best answer to
   "why didn't my agent bid?", which is the support question this product will get most.
8. **Purchase orders.** Generate a PDF PO from an agreed match, with the verified business details and the
   agreed terms. It is what makes a deal real to an accountant — and the artefact a lender asks for.
9. **Partial and multi-supplier awards.** Split an RFQ between two suppliers (the spec already reserves
   multi-unit). Routine in wholesale and currently impossible.
10. **Seller analytics.** Win/loss, distance from the winning price, best hour to list. All derivable from
    data already stored.

**Later, and bigger**

11. **Invoice and inventory financing.** A record of completed deals with a reputation attached is precisely
    what a lender wants and what an SME cannot otherwise prove. Refer, revenue-share, stay out of the credit
    risk. This is the natural second business.
12. **WhatsApp-first selling.** List by sending a photo and a price. The right surface for this market — but
    only after the channel-authority fix in item 4 above.
13. **ERP and bookkeeping integration.** QuickBooks and Zoho are common in Kenyan SMEs; a public API with
    webhooks matters more than any individual connector.
14. **Collusion detection.** The shill-bid guard catches one account bidding on itself. Bidding rings need
    graph analysis over time — worth building once there is enough volume for the signal to exist.

## What I would do in order

1. Archive closed records out of memory (item 1) — it is the only ceiling that does not move with hardware.
2. Index the sign-in path (item 3) and narrow channel commands (item 4) — both small, both real.
3. `SIGTERM` drain plus a documented restart window (item 2).
4. Agent presets, the agent timeline, and the price index — three cheap features that address sign-up
   conversion, support load, and marketing respectively.
5. Scope settlement with a payments partner in parallel, because it has a lead time nothing else here has.
